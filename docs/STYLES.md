# Модель стиля tuidom

> Внутренняя спецификация (ADR-глубина, для мейнтейнеров). User-facing
> документация — [GUIDE.md](../GUIDE.md).

Три тезиса модели: **каскад — единственный источник цвета на отрисовке;
состояния разрешает ядро; цвета адресуются токенами-переменными**. Прецеденты:
CSS (псевдоклассы + custom properties), эволюция самого VS Code от
`IStyles`-структур к `--vscode-*`-переменным, Textual.

## Декларация: TUIStyle

```ts
element.style = {
    fg: "menu.foreground",                 // число | сентинел INHERITED_* | имя токена
    bg: INHERITED_BG,
    when: [                                 // варианты по состояниям
        { states: ["hover"], bg: "list.hoverBackground" },
        { states: ["selected"], fg: "...", bg: "..." },
        { states: ["selected", "in:focus"], bg: "..." },
    ],
};
```

- **when-запись применяется, когда активны ВСЕ её селекторы (AND); позже
  объявленная активная запись побеждает** — порядок = приоритет, как порядок
  правил CSS. `states: []` легален («всегда активна»).
- Селектор `"x"` — состояние на самом элементе; `"in:x"` — на себе или любом
  предке (замена descendant-комбинатора; ключ к active/inactive selection:
  строка объявляет `["selected", "in:focus"]`, а focus-состояние стоит на
  списке). Осторожно: `in:hover` шире CSS-`:hover` — светится и когда курсор
  на сиблинге внутри hovered-контейнера.
- Сеттер `style` сравнивает по значению (`styleEquals`) — повторный пуш равного
  объекта (пере-применение темы, пересборка виджета) не дирявит поддерево.

## Состояния

Набор активных состояний живёт на элементе (`setStyleState`/`hasStyleState`/
`activeStyleStates`). **hover и focus ведёт ядро**: hover — диспатчер мыши по
всей цепочке target→root (как `:hover`; при pointer capture заморожен), focus —
FocusManager только на target (как `:focus`). Состояние обновляется ДО диспатча
mouseenter/mouseleave/blur/focus — слушатели видят его консистентным.
Произвольные строковые состояния ("selected", "checked", "active", "lit", …)
виджеты ставят программно; смена состояния перерезолвит стиль элемента и
поддерева.

Состояния читают и мимо каскада: `hasStyleState` — своё, `hasStyleStateWithin`
— своё или предка (рантайм-двойник `in:`). Второй нужен тем, кто решает не
цветом, а **геометрией**, и потому обязан знать состояние ещё в `performLayout`,
до стилевого прохода. Так живёт инлайн-кнопка Open File в строке Source Control:
`ListViewElement` ставит на обёртку строки `LIST_ROW_ACTIVE_STATE`
(«под указателем ИЛИ под курсором сфокусированного списка»), а корень строки по
нему отдаёт кнопке колонки — или ноль, и всё место достаётся имени файла.
Отдельное состояние здесь не прихоть: `in:hover` не подошёл бы, потому что
строки списка презентационные, target мыши — сам список, и hover стоял бы на
предке всех строк разом.

**Дети наследуют РЕЗУЛЬТАТ резолва родителя с учётом его состояний** — hover-фон
строки списка автоматически течёт в её презентационные метки, а явные
посимвольные подсветки (charStyles с конкретными цветами) выделение переживают.
Именно это убило пост-рендерные патчи ячеек в listView.

## Токены-переменные (аналог CSS custom properties)

`StyleColor = number | имя токена`. Таблицы токен→число каскадируют по дереву
(`setStyleVars`, обычно только на корне), дно цепочки — `STYLE_TOKEN_DEFAULTS`
(`packages/core/src/dom/styles/styleTokens.ts`) — **единственное место RGB-литералов
tuidom**. Правило: токен, на который ссылается виджет elements, обязан иметь
дефолт там — иначе тесты/stories без хостовой таблицы упадут fail-fast'ом.

- Имена — в конвенции color id VS Code (`"list.activeSelectionBackground"`);
  tuidom-специфика без эквивалента — под своим именем (`menu.shortcutForeground`,
  `quickPick.*`, `menuBar.*`, `titledPanel.*`).
- Незнакомый токен — **throw с именем класса и токена** на первом же кадре
  (наш fail-fast; опечатки хостовых ключей компилятор не ловит — типизирован
  только автокомплит по дефолтам).
- Painter-виджеты (editor, terminal, деревья) читают токены в render
  через `styleVar(name)`; `styleVar(name, fallback)` — для токенов, чьё
  отсутствие ЛЕГАЛЬНО означает «взять из каскада» (`editorGutter.background` →
  фон редактора). `resolveColor(color)` резолвит StyleColor из ДАННЫХ
  (посимвольные стили, `ITreeItem.iconColor` — провайдеры отдают
  `gitDecoration.*`, раскраска переживает смену темы без пере-пуша).
- Значения таблиц — только конкретные числа (`isColorValue`: RGB, RGBA,
  `DEFAULT_COLOR`, `TRANSPARENT_COLOR`); сентинелы INHERITED_* в таблицах
  запрещены (assert).

## Модель цвета: альфа и композитинг

Цвет — число (`packages/core/src/common/colorUtils.ts`). Непрозрачный —
прежнее 24-битное `0xRRGGBB` (`packRgb`); **весь существующий код с такими
литералами валиден без миграции**. Полупрозрачный — `0xAARRGGBB` беззнаково
(`packRgba(r, g, b, a)`, альфа 1..254 в старшем байте, число > 0xFFFFFF, так что
`isTranslucent` — одно сравнение). Альфа 255 нормализуется в 24-битное число,
альфа 0 — в сентинел `TRANSPARENT_COLOR` (старший байт 0 занят непрозрачными,
а RGB прозрачного цвета не значит ничего). Строки тем разбирает
`parseHexColor` (`#RGB`/`#RGBA`/`#RRGGBB`/`#RRGGBBAA`), обратно —
`formatHexColor`. Упаковка сознательно через умножение, а не `<<`: сдвиг дал
бы отрицательные числа, и непрозрачный белый совпал бы с `DEFAULT_COLOR`.

**Композитинг — в порядке отрисовки, как в браузере у VS Code**, через
`compositeOver(color, under)` (source-over, результат всегда непрозрачен).
Терминал альфы не умеет, поэтому смешивание выполняется в двух точках, а
бэкенды, снапшоты и SVG видят уже готовые непрозрачные цвета:

1. **Грид** (`Grid.updateCell`/`setCell`): `bg` с альфой ложится на текущий bg
   ячейки — то, что уже нарисовано в ней в этом кадре (фон родителя, подсветка
   строки); `fg` с альфой — на итоговый bg ячейки. Это путь патчей ячеек
   painter-виджетов (`setCell({ bg })` подсветок диапазонов, `drawText` с
   цветами из `styleVar`/`resolveColor` — они отдают токен **как есть**, с
   альфой). Выделение поверх подсветки текущей строки даёт смесь смеси; порядок
   слоёв = порядок `setCell`. Ячейки грида хранят только непрозрачное.
2. **Каскад** (`performStyleResolution`): собственный `bg` элемента с альфой
   композитится с унаследованным bg, `fg` — с итоговым bg; в `resolvedStyle` и
   детям уходят непрозрачные значения. Иначе заливка фона (`paintOwnBackground`)
   и текст, нарисованный тем же `resolvedStyle.bg`, легли бы на ячейку двумя
   слоями. Подложка здесь — bg родителя по каскаду, а не пиксель под элементом:
   для дерева, где дети рисуются внутри родителей, это одно и то же; оверлей с
   полупрозрачным `bg` в стиле смешается с фоном по каскаду, а не с контентом
   под собой (хочется настоящего — красить патчами через `getCell`/`setCell`).
   Вложенные полупрозрачные фоны накладываются друг на друга (по слою на
   элемент), `INHERITED_BG` перезаливает уже скомпозиченным цветом родителя.

Правила краевых случаев:

- **Подложка `DEFAULT_COLOR`** (цвет терминала, нам неизвестен): смешивать не с
  чем — альфа отбрасывается, цвет ложится непрозрачным. У хоста с непрозрачным
  корнем не случается; damage-проход всегда начинается с корня, и его фон
  ложится в очищенную область первым (тест
  `tuiApplication.damage.alpha.test.ts`).
- **`TRANSPARENT_COLOR`** как собственный `bg` — элемент не красит
  (`hasOwnBackground === false`, как CSS `transparent`); как патч — no-op; как
  `fg` — цвет подложки (невидимый текст).
- Полупрозрачный `fg` зависит от bg, а не от прежнего fg ячейки, поэтому
  повторная запись идемпотентна. Полупрозрачный `bg` патчами — нет: два
  `setCell({ bg })` одним цветом в одну ячейку дают два слоя. Painter, который
  залил область и затем пишет текст, передаёт в `drawText` уже непрозрачный bg
  (из `resolvedStyle` или прочитанный `getCell`), а не токен с альфой.

## Заливка фона

База `render()` заливает прямоугольник элемента `resolvedStyle.bg`, если bg
задан СОБСТВЕННЫМ стилем (базой или сработавшим when-вариантом); без
собственного bg элемент прозрачен, как в CSS. `INHERITED_BG` — намеренная
перезаливка цветом родителя (так устроен FillerElement), `INHERITED_FG` —
инверсия. Кастомный painter зовёт `paintOwnBackground(context)` сам. Bg с
альфой заливается уже скомпозиченным с унаследованным (см. «Модель цвета»),
`TRANSPARENT_COLOR` — не заливается вовсе.

## Тень оверлея

`TUIElement.shadow = true` (для сессий слоя — `OverlaySessionOptions.shadow`) —
TUI-аналог `box-shadow` у попапов VS Code: колонка справа и строка снизу от
элемента (сдвиг 1×1) затемняются токеном `widget.shadow` — полупрозрачным
цветом, который композитится с тем, что уже нарисовано в этих ячейках (bg —
гридом, fg — при отрисовке тени; терминальный `DEFAULT_COLOR` у fg не
трогается). Рисует **родитель** после ребёнка (`renderChildren`,
`OverlayLayer.render`): клип ребёнка не выпускает его за собственный rect (Н2),
а тень лежит снаружи; damage-rect элемента при этом расширяется на
`paintOutset` (1), чтобы тень перерисовывалась при переезде и скрытии; тень
не зависит от того, попал ли сам ребёнок в клип — damage только по полосе тени
(перерисовался виджет под ней) кладёт её заново. Широкий глиф (CJK, эмодзи) под
кромкой тени затемняется целиком — голова тянет цвета в продолжение, тень на
этой строке шире на колонку; продолжение глифа самого ребёнка у его правой
кромки не трогается. `TRANSPARENT_COLOR` в токене — тени нет. `shadow` в
опциях сессии не задан — остаётся `element.shadow`, как выставил владелец.
По умолчанию тень выключена у всех элементов и сессий, включая меню, дропдауны и
select-списки tuidom: это возможность движка, а включает её хост у тех попапов,
где решил её использовать. Зачем: темы вроде Catppuccin рисуют
`menu.border` цветом фона меню и полагаются на тень — без неё меню растворяется
в редакторе того же цвета.

## Доставка темы (контракт хоста)

Одна точка: хост кладёт всю палитру активной темы в корневой var-scope одним
вызовом `root.setStyleVars(vars)` (в Vexx это делает `applyThemeVars` в
`themeStyleVars.ts`; в тестах — снапшот Dark+ из
`testing/darkPlusStyleVars.ts`). Hot-swap темы = повторный вызов, дерево
перерезолвится каскадом. Компоненты задают ИМЕНА токенов в `style` своих
контролов один раз при создании и тему не слушают. Фоллбэки хостовых мостов
(`terminal.background ?? panel.background`, `terminal.foreground ??
editor.foreground`) — на стороне хоста при формировании словаря vars;
`editorGutter.background ?? editor.background` — fallback на месте чтения.

В тестах: TestApp кладёт палитру dark+ в корень (паритет с приложением);
standalone-рендеры tuidom-виджетов живут на дефолтах STYLE_TOKEN_DEFAULTS;
хостовым компонентам (`sideBar.*`, `statusBar.*` — без дефолтов tuidom) —
`renderElement(..., { themeVars: true })` либо явная таблица styleVars.

## Зафиксированные решения

- Числовой `tabIndex`-подобный порядок и z-index не появились; когда-нибудь
  понадобившийся приоритет состояний выражается порядком when-записей и
  закрывается styling-тестами (типы его не ловят).
- Расширение стиля — when-варианты и токены, не наследование интерфейса
  (дженерик `TUIElement<S extends TUIStyle>` отвергнут).
- Hover списков включён по умолчанию (`list.hoverBackground`) и не меняет fg;
  токен `list.hoverForeground` и `notifyDetached` (залипание hover при detach
  до следующего mousemove) — аддитивно позже, см.
  [TODO/AdditiveFeatures.md](TODO/AdditiveFeatures.md).
