# ListViewElement vs TreeViewElement: критерий выбора и техдолг

Два списочных контрола сосуществуют **осознанно, это не переходное состояние**
(см. [arch/TUIDom.md](../arch/TUIDom.md), раздел ListViewElement):

- `TreeViewElement` — data-driven дерево: хост отдаёт данные провайдером
  (модель vscode `TreeDataProvider`), контрол сам строит строки. Нужен, пока
  внешние API хостов устроены именно так.
- `ListViewElement` — императивные строки-элементы (`appendRow`) с
  виртуализацией; для собственных списков хоста с богатыми строками
  (посимвольная подсветка, инлайн-кнопки на делегации кликов).

Задачи:

- **Зафиксировать критерий выбора** в доке (сейчас размазан по arch/TUIDom.md)
  и свести общие механики (курсор/мультивыбор/typeahead/клавиатура) к одному
  описанию — реализации обязаны держать их 1:1.
- **Техдолг двух реализаций**: общая клавиатурно-курсорная логика дублируется;
  решить — выносить общее ядро или зафиксировать дублирование как цену
  независимости контролов.
- **Фоллбек полной пересборки проекции** `appendRow`: вставка в середину и
  collapse/hidden пересобирают материализованную проекцию целиком (O(N));
  инкрементальный путь есть только для append в хвост
  (`listViewElement.appendCost.test.ts`). Оценить, нужен ли инкрементальный
  путь и для этих случаев.

Критерий готовности: критерий выбора записан в доке одним разделом; по техдолгу
и фоллбеку принято и записано решение (сделать или осознанно оставить).
